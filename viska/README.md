# viska：FormSight 的验证与门禁资产

> 本目录是 FormSight 仓库内的验证资产层。门禁规则、门账结构与执行命令都在本目录内自洽，
> 不依赖仓库外的任何路线图文档。

## 1. 定位与边界

viska 每天处理的对象是**改动**，不是模型。它回答一个问题：

> 这次改动有没有破坏仓库里已经被验证过的契约与不变量？

明确不做：

- 不存会话 transcript，不做回滚，不做调度器；
- 不做 Web Dashboard、持久化队列、数据库；
- 不做模型排行榜或通用 eval 框架；
- 不定义“什么算业务失败”——底层仍由 vitest / biome / tsc 执行。

## 2. 当前状态

| 项目 | 状态 |
|---|---|
| 靶场 | FormSight（单线程，同一时期只挂载一个仓库） |

## 3. 快速开始

```bash
pnpm install          # 安装依赖
pnpm verify           # 提交前必跑：biome + tsc + 架构阻断子集 + vitest
pnpm check:arch       # 单独查看架构坏味道阻断 / 咨询子集
pnpm exec vitest run src/storage/__tests__/planStorage.test.ts   # 单文件快速回归
```

时延约束：`pnpm verify` 的本地 p50 必须低于 **60 s**，硬上限 **90 s**。
超过 120 s 且无法快速优化时，按规范剔除长耗时用例，不得靠删除断言降耗时。

## 4. 三道门

| 门 | 周期 | 要解决的失败 | 当前 |
|---|---|---|---|
| **Gate 1** | 第 1–4 周 | 代理宣称“完成”，但无法在 60 s 内判定契约是否被破坏 | **进行中** |
| **Gate 2** | 第 5–8 周 | Diff 过大、审查靠肉眼，架构规范无法自动报错 | 未开始 |
| **Gate 3** | 第 9–12 周 | 替换模型 / Prompt / 工具接口时只能靠体感判断 | 未开始 |

门只有两种状态：开 / 关。关门标准是“自动检查改变了某个决定”，不是“学完了某章”。

## 5. 门账规范

### 5.1 唯一信源

[`ledger.md`](./ledger.md) 是门禁生命周期的唯一定义。新增、修复或退役一条检查时，
必须同步更新对应行；禁止只在对话或提交信息里记录。

### 5.2 字段

| 字段 | 含义 |
|---|---|
| `ID` | 门编号-序号，例如 `G1-01`；ID 不复用 |
| `靶场` | 所属仓库，当前固定为 `FormSight` |
| `真实失败根因` | 来自真实提交 / 真实故障，不写玩具场景 |
| `关联守护检查` | 测试文件 + 用例名，或命令入口 |
| `能力级` | L1 定义 Oracle / L2 高信噪比用例 / L3 自动化门禁 / L4 门禁驱动决策 / L5 体系迁移 |
| `状态` | `open` / `closed` / `retired` |
| `最近运行` | 最近一次实际执行日期，使用 `+08:00` 语义 |
| `最近拦截` | 最近一次拦截真实违规改动的日期；没有则写 `-` |
| `责任归属` | `agent` / `human` |
| `退役倒计时` | `核心契约（永驻）` 或 `90天无红` 等退役条件 |

### 5.3 状态机

- `open`：检查已就绪，尚未在真实开发中拦截过违规改动；
- `closed`：已至少成功拦截一次，处于守门状态；
- `retired`：已确认无用或被上层契约覆盖，安全移除并记录原因。

### 5.4 退役规则

一条检查若连续 **90 天**未报红，且不守护对外公开数据契约或高风险状态，
强制从仓库删除并在门账记入 `retired`；禁止靠白名单静默保留。

### 5.5 观测点

任何随机器/网络/工具链变化的环境断言，必须带观测点：

```text
观测点 <node> / <YYYY-MM-DD> / <方向>
```

- 公开仓库只写假名 `n1`（或后续 `n2`），真实机器名、绝对路径、精确耗时写入
  `viska/local/baseline.md`（被 gitignore）。
- 时间使用 `+08:00` 偏移；只写日期时默认按本地日期理解。

## 6. 新增一条回归（红 → 绿）

1. 从近 90 天真实 `fix:` 提交中选定一个故障场景；
2. 切到该修复的**父提交**，写一条能稳定报红的最小复现测试，记录失败输出；
3. 切回修复提交，确认同一条测试变绿；
4. 在 [`ledger.md`](./ledger.md) 增加一行：真实失败根因、关联检查、状态、观测点；
5. 运行 `pnpm verify`，确认全量绿且无 Flake；
6. 在回复中附上 verify 摘要与红绿证据。

禁止：修改/删除既有测试来变绿、加 `skip` / `only`、使用 `--no-verify`、
或通过放宽 lint 规则绕过失败。

## 7. 目录职责

```text
viska/
├── README.md              # 本文件：自洽的验证系统说明
├── ledger.md              # 门账（公开安全，无本机细节）
├── baseline.example.md    # 机器基线模板（跟踪）
├── .gitignore             # 忽略 local/ 与 packets/
└── local/
    └── baseline.md        # 本机实测：路径、耗时、工具版本、节点映射（忽略）
```

- `viska/local/`：永不跟踪；新机器复制 `baseline.example.md` 后填写。
- `viska/packets/`：Gate 2 生成的审查包，默认忽略，避免把含 diff 的文件误提交。
- `AGENTS.md` 留在仓库根目录，是代理发现入口；它只负责执行规则，不复制门账。
- 测试仍与源码同级放在 `src/**/__tests__/`，本目录只登记，不复制用例。

## 8. 隐私规则（公开仓库）

公开的 `ledger.md` / `README.md` 禁止出现：

- 绝对路径（`/home/...`、`C:\...`）；
- 邮箱、Token、API Key、私钥；
- SSH 别名、内网 IP、出口 IP；
- 真实主机名（用 `n1` 等假名替代）。

机器相关事实只写 `viska/local/baseline.md`。提交前可运行：

```bash
git grep -nE '/(home|Users)/|[A-Za-z]:\\\\|([0-9]{1,3}\.){3}[0-9]{1,3}|sk-[A-Za-z0-9]{16,}|ghp_[A-Za-z0-9]{20,}' -- . ':!pnpm-lock.yaml'
```
