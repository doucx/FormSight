# ADR 0004：v0.x 是破坏性字段归一化的唯一窗口

- 状态：已采纳（2026-09）
- 证据：`mode` 字段已从 `UnifiedTrialRecord` 删除；`cardId` 成为唯一键；prune 已移除

## 背景

重构期出现过两次相反的判断：

1. 先判"删除 `cardId || mode` 双主键是负 ROI，永不清洗"，理由是迁移可能毁掉用户本地库，于是保留读时兼容垫片；
2. 后判"v0.x 是唯一廉价窗口，P0 立即归一化"，理由是兼容垫片会按读取点数量线性复制，而用户量极小时迁移成本最低。

最终执行了后者。

## 决策

**v0.x 阶段直接做破坏性归一化，不为旧字段保留读时兜底。v1.0 之后改为只增不删。**

- 允许：删字段、改主键语义、重写聚合、删死代码路径。
- 要求：迁移脚本 + 版本标记（`app_metadata`）+ 导入旧备份时的显式升级路径。
- 禁止（v1.0 起）：删除字段、改写主键语义；只允许新增字段 + 默认值 + 迁移。

## 理由

- 兼容垫片的成本按**读取点数量**增长，而读取点只会变多；迁移脚本的成本按**版本数**增长，且只在升级瞬间付一次。
- 用户量小时，迁移失败的 blast radius 最小；等有了长期用户数据，同一个迁移就变成高风险操作。
- 垫片会掩盖类型问题：`mode ?? resolveLegacy(...)` 让"到底以谁为准"永远模糊。

## 代价

- 旧版本导出的备份必须经过升级路径，不能直接消费。
- 每次归一化都要写迁移与版本标记，短期开发变慢。
- 一旦 v1.0 发布，这个窗口永久关闭；此后再想清理只能等 v2 或做双写。

## 复核条件

- 出现第一份真实外部用户的长期数据；
- 或版本号到达 1.0（此后策略切换为只增不删）；
- 或一次迁移导致本地库不可恢复的真实事故（此时应补导出前置，而不是恢复垫片）。

## 后果

- `src/storage/db/schema.ts#UnifiedTrialRecord` 是这条决策的锚点。
- 新增统计维度时不再问"旧记录怎么办"，而是问"迁移脚本怎么写"。
- HAP `root` scope 有对应 `DECISION COMPAT` 记录，复核触发 `event:v1_release`。
